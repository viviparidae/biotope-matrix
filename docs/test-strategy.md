# テスト戦略

## 1. 目的とトレーサビリティ

要求仕様書と Feature ファイル、実装テストの3層を必ず対応づける。要求 ID は `REQ-*` とし、Feature のタグ、`describe` / `it` 名、そして CI 発行レポートで一貫して追跡可能にする。要求網羅率は、対象要件に少なくとも 1 件の合格テストが紐づいた数を総数で割って算出し、未カバー要件を PR のレポートに出力する。

## 2. 三層トレーサビリティ

1. 要件層: `docs/requirements.md` に要件 ID、概要、評価基準を記載する。
2. BDD 層: `tests/features/*.feature` に `@REQ-...` を付けてシナリオを記述する。
3. 実装層: `vitest` のテスト名、コメント、`it` のラベルに `REQ-...` を付与する。

> 例: `REQ-PRED-001` は要求仕様、Feature での `@REQ-PRED-001`、そして `predation` テストの `it('REQ-PRED-001: ...')` が同一の要求を参照する。

## 3. ブラックボックス設計技法

- 同等性分割: 有効・無効の入力クラスを分け、代表ケースを選ぶ。
- 境界値分析: 閾値 `N` では `N-1`, `N`, `N+1` を最低限検証する。サイズ比率、飢餓閾値、視野距離、エネルギー変動が対象。
- 状態遷移テスト: 生存、飢餓、追跡、捕食成功、失敗、死亡の遷移を N=1 で確認する。
- ペアワイズ法: `shape`、`size`、`energy`、`species` を組み合わせる場合は、全組み合わせではなく全ペアの検証のみに絞る。

## 4. テスト構造と品質ゲート

- 単体テストは AAA を守り、Arrange / Act / Assert を明示する。
- 固定乱数を注入し、判定ロジックを決定的にする。
- ECS コアは DOM / Canvas / Web Audio へ依存しない。
- PR の品質ゲートは、型チェック、`vitest`、Feature 検証、要求 ID 未カバー確認で構成する。

## 5. Cucumber と受入テスト

利用者やドメインエキスパート向けの振る舞いは `tests/features/*.feature` に Gherkin で記述し、`tests/steps/*.steps.ts` に step 定義を分離する。各 feature の先頭タグとして要求 ID を付け、`pnpm test:cucumber` で受入テストを実行する。step 定義は Arrange / Act / Assert を混在させず、観察可能な結果を検証する。

## 7. CI での実行方針

- `pnpm test` で単体・統合・受入の回帰を実行する。
- `.github/workflows/fitness.yml` で `1 フレーム処理時間` と `起動依存チェック` を自動実行する。
- 観測不能な要件は、Feature への紐付けと要求 ID の明示を必須とする。

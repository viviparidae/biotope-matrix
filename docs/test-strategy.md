# テスト戦略

## 1. 目的と要求網羅率

要求仕様書の要件 ID（`F-01`〜`F-10`、`NFR-01`〜`NFR-12`、および拡張要件）をテストケースへ紐付ける。テスト名、テストコメント、またはケース表に ID を必ず記載し、要求から自動テスト・受入テストまで追跡できるようにする。

要求網羅率は、少なくとも一つの合格テストが紐付いた要件 ID の数を、対象要件 ID の総数で割って算出する。分母・分子と未カバー ID を CI のレポートへ出力し、コードカバレッジだけで要求充足を代替しない。

## 2. ブラックボックス設計技法

- **同等性分割**: 入力を同じ振る舞いになる有効・無効クラスへ分け、各クラスから代表値を選ぶ。閾値がある場合は境界値分析を優先する。
- **境界値分析**: 閾値 `N` について `N-1`、`N`、`N+1` を最低限テストする。サイズ比率、飢餓エネルギー、個体数上限、視野・接触距離を対象とする。
- **状態遷移テスト**: 生存、飢餓、追跡、反撃、捕食成功、死亡の状態を定義し、1-switch（N=1）で各状態からの単一遷移を検証する。重要な連鎖は複数遷移も追加する。
- **ペアワイズ法**: 形態、サイズ帯、エネルギー状態、環境、対象種など複数パラメータの組み合わせは、全組み合わせではなく全ペアが少なくとも一度現れるケース集合を作る。

## 3. テスト構造と品質ゲート

単体テストはドメインの観察可能な結果を対象にし、AAA（Arrange / Act / Assert）で記述する。固定乱数を注入し、判定ロジックを決定的にする。ECS のコアは DOM、Canvas、Web Audio API に依存させない。

PR の品質ゲートは、型チェック、全単体・統合テスト、要求 ID の未カバー確認とする。性能要求は個体数別ベンチマークで平均 FPS、95 パーセンタイル更新時間、フレーム内割り当てを測定する。

## 3.1 Cucumber による受入テスト

利用者やドメインエキスパートが読める振る舞いは `tests/features/*.feature` に日本語 Gherkin で記述し、実行可能な step 定義を `tests/steps/*.steps.ts` に分離する。各 feature のシナリオは要求 ID を名前またはコメントで追跡可能にし、実行は `pnpm test:cucumber` で行う。step 定義では Arrange / Act / Assert の責務を混在させず、判定結果などの観察可能な結果を検証する。

## 4. 拡張要件の追跡

| 要件 ID | 対象 | 主な技法 |
| --- | --- | --- |
| REQ-MORPH-001 | サイズ・形態の保持と遺伝変異 | 同等性分割、境界値 |
| REQ-PRED-001 | サイズ・攻撃・防御による捕食成功判定 | 境界値、ペアワイズ |
| REQ-CANN-001 | 飢餓時に小型肉食個体を捕食対象にする | 状態遷移 N=1、境界値 |
| REQ-FLOCK-001 | 空間グリッドによる分離・整列・結合 | 同等性分割、性能測定 |

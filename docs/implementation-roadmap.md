# 生態系シミュレーション（pythagora-bios）実装ロードマップ

このロードマップは、[要求仕様書](requirements.md)の `F-01`〜`F-10` と `NFR-01`〜`NFR-12`、および[アーキテクチャ設計書](architecture.md)のECS・Worker・Kubernetes設計を、短時間で完了・検証できるIssueへ分解したものである。

## Phase 1: MVP / 単一ノードPoC（Web画面での自律動作）

### Issue #1: [Phase 1] ECSコアエンジンおよびCanvas描画ループの構築
* **概要**: ブラウザ上で固定tickのECS Worldを更新し、描画フレームレートとシミュレーション更新を分離する。Entity ID、SoA Component、System実行順序、Command Buffer、再利用可能なIDをMVPの最小範囲で実装する。
* **完了条件**:
  - [ ] TypeScriptでEntity、Position、Velocity、Life、SpeciesのSoA Componentを定義する
  - [ ] Entityの生成・`alive=false`化・tick末尾の削除・ID再利用を実装する
  - [ ] `requestAnimationFrame` と固定tickのメインループを分離する
  - [ ] Canvas 2Dへ `1x1`〜`3x3` pxのドットを描画できる
  - [ ] 描画ループ内で配列・オブジェクト・クロージャを毎フレーム生成しない
  - [ ] Entityの再利用、tick順序、描画呼び出しを固定乱数またはモック時計で単体テストする

### Issue #2: [Phase 1] 草・草食個体・肉食個体の基本ライフサイクル実装
* **概要**: 草の生成・自然枯死、草食個体の採餌・回復・分裂、肉食個体の追尾・捕食・徘徊を、Perception、Behavior、Movement、Interaction、Lifecycleの順序で実装する。直接のEntity変更は避け、Command Bufferでtick末尾に確定する。
* **完了条件**:
  - [ ] 草を1秒ごとに判定し、100株未満かつ発生可能な環境で1株生成する
  - [ ] 発生から30秒経過した未捕食の草を枯死させる
  - [ ] 草食個体が半径5px以内の最寄りの草へ移動し、接触時に草を消してエネルギーを50増加させる
  - [ ] エネルギーが150を超えた草食個体を、親子75ずつへ分裂させる
  - [ ] 肉食個体が半径100px以内の最寄りの草食個体を追尾し、接触時に捕食してエネルギーを100増加させる
  - [ ] 捕食対象がない肉食個体をランダム方向へ徘徊させる
  - [ ] `F-01`〜`F-03`の各Gherkinシナリオを固定seedのECSテストで検証する

### Issue #3: [Phase 1] 突然変異・代謝・個体数連鎖・境界反射の実装
* **概要**: 分裂時の遺伝変異と速度依存の代謝、画面端での反射、捕食者絶滅時の補充、大繁殖から捕食者増加へ至る基本連鎖を追加する。未指定の閾値は設定値としてまとめる。
* **完了条件**:
  - [ ] 子の速度と視野を親からそれぞれ±10%の範囲で変異させる
  - [ ] 速度に応じてエネルギー消費量を変化させ、低温・明るさの補正用フィールドを受け取れる形にする
  - [ ] 上下左右の端で該当軸の速度ベクトルを反転させる
  - [ ] 肉食個体が0体かつ草食個体が30体を超えた場合に補充する
  - [ ] 草食個体50体到達時の草の成長速度3倍と、その後の捕食者増加をイベント連鎖として記録する
  - [ ] 閾値、初期個体数、変異率を型付き設定として外部化する
  - [ ] `F-04`、`F-05`と状態ハッシュ・イベント連番の決定性をテストする

## Phase 2: 生態系循環・演出・サウンド（ピタゴラスイッチ化）

### Issue #4: [Phase 2] 死骸・分解者エフェクト・土壌栄養の循環システム実装
* **概要**: 草食個体・肉食個体の死亡地点に死骸を残し、分解の進行、分解者エフェクト、栄養度の上昇、高栄養エリアでの草の高密度生成を実装する。死骸とエフェクトは短命Entityとして再利用可能な領域で管理する。
* **完了条件**:
  - [ ] 個体死亡時に死亡位置・分解度・栄養収量を持つ死骸を生成する
  - [ ] 分解者密度に応じて分解度を進め、完了時に死骸を消去する
  - [ ] 分解中に視覚的な分解者エフェクトを生成し、過剰生成を上限で抑える
  - [ ] 分解収量を地形セルの栄養度へ一度だけ加算する
  - [ ] 分解完了後も高栄養エリアを一定時間維持し、草の生成率を上げる
  - [ ] 死骸の二重分解、栄養の二重計上、ID世代違いのイベントをテストする

### Issue #5: [Phase 2] 地形変貌・災害イベント・視覚状態表現の実装
* **概要**: 草の枯渇、分解者の滞留、捕食集中を地形セルの履歴から判定し、砂漠・湿地・山へ変化させる。個体数・湿度・分解者密度を入力に隕石、水流、ゾンビ化をイベントとして発火させる。
* **完了条件**:
  - [ ] 地形セルごとに肥沃度、イベント熱、湿度、種別をSoAまたは連続グリッドで保持する
  - [ ] 草の枯渇地点を砂漠化し、移動速度を低下させる
  - [ ] 分解者エフェクトの滞留地点を湿地化し、草の成長率を10倍にする
  - [ ] 捕食集中地点を山へ隆起させ、個体が通過できない壁にする
  - [ ] 隕石でクレーターと死骸、水流で位置シャッフル、閾値超過で紫色ゾンビを生成する
  - [ ] 地形種別だけに依存せず、模様・点滅・形状を含む視覚表現で災害状態を判別できる
  - [ ] `F-08`の各トリガーを固定seedで再現し、イベント連番を検証する

### Issue #6: [Phase 2] 明るさ・温度・Web Audio APIによる環境音の実装
* **概要**: 明るさ・温度を環境Componentとしてtick境界で適用し、草の生成、視野、速度、代謝を変化させる。イベントからOscillator、Gain、BiquadFilter、StereoPannerを組み立て、描画を妨げずに自動生成音を再生する。
* **完了条件**:
  - [ ] 夜間は草の発生を停止し、個体の有効視野を50%にする
  - [ ] 10℃未満では移動速度を30%低下させ、体温維持分の消費を加算する
  - [ ] 移動・捕食・繁殖・災害を音声イベントへ変換し、位置を左右パン、状態をピッチへ反映する
  - [ ] 安定時はチルな和音、繁殖・災害時は速い不協和音へ遷移する
  - [ ] AudioContextはユーザー操作後に開始し、拒否・未対応時もCanvas描画を継続する
  - [ ] AudioNodeの構成、音量上限、解放ライフサイクルをモックでテストする
  - [ ] `F-06`、`F-09`、`NFR-08`、`NFR-11`の受け入れ条件を確認する

## Phase 3: 分散スケーラビリティ & K8s オーケストレーション

### Issue #7: [Phase 3] 空間グリッド分割と近傍探索の最適化
* **概要**: フィールドを固定サイズの空間グリッドまたはSpatial Hashへ分割し、草食個体の5px、肉食個体の100pxの近傍探索を局所化する。描画用Packed Snapshotとシミュレーション用SoAの境界も定義する。
* **完了条件**:
  - [ ] Entityの所属セルをtickごとに更新し、再利用可能なバッファへ登録する
  - [ ] 視野半径に応じて必要セルだけを探索し、最寄り対象を返す
  - [ ] 空セル、境界セル、Entity削除後の古い参照を安全に処理する
  - [ ] 全探索と比較して近傍探索の計算量・処理時間を計測する
  - [ ] 数千Entityで平均30 FPS以上、更新・描画95パーセンタイル33ms以下を確認する
  - [ ] 近傍結果と個体数が全探索版と一致するテストを追加する

### Issue #8: [Phase 3] Workerプロセス分離・購読Gateway・個体ハンドオーバーの実装
* **概要**: シミュレーション正本をWorkerへ移し、Frontendはスナップショットを購読する構成へ分離する。Shard境界を越える個体をtick境界で一度だけ移送し、Leader Worker、イベント連番、チェックポイントで再接続と復旧を成立させる。
* **完了条件**:
  - [ ] Workerが固定tickでECSを実行し、Frontendへ差分または完全スナップショットを配信する
  - [ ] Gatewayが購読、認証、レート制限を担当し、Entity状態を直接変更しない
  - [ ] Shard境界を越えるEntityをハンドオーバー命令として確定し、送信元・送信先で二重実行しない
  - [ ] Leader Lease失効後にのみ候補Workerが昇格し、同一Shardの二重Leaderを防ぐ
  - [ ] チェックポイント、イベント連番、状態ハッシュからWorkerを再開できる
  - [ ] 切断後の`lastSequence`から欠落差分または最新スナップショットへ復帰できる
  - [ ] Worker停止・再接続・ハンドオーバーをローカル統合テストで検証する

### Issue #9: [Phase 3] CRD・ConfigMap・メトリクスとHPA/KEDAオートスケールの実装
* **概要**: `BiotopeEnvironment` CRDとバージョン付きConfigMapで環境値・閾値を配布し、Operatorが検証して次tick境界へ適用する。個体数・CPU負荷・主要イベントをメトリクス化し、HPA/KEDAでWorkerをスケールさせる。
* **完了条件**:
  - [ ] `BiotopeEnvironment` CRDに明るさ、温度、湿度、閾値、スキーマバージョンを定義する
  - [ ] Operatorまたはローカルモックが不正値を拒否し、`environmentVersion`を単調増加させる
  - [ ] 全Workerへ設定を配布し、同一tick境界で適用したことをログで確認できる
  - [ ] 個体数、CPU負荷、tick時間、イベント数、再接続数を構造化ログ・メトリクスへ出力する
  - [ ] 個体数またはCPU負荷80%超過をHPA/KEDAのスケール条件として設定する
  - [ ] readiness probe、liveness probe、リソース制限をWorker DeploymentまたはStatefulSetへ設定する
  - [ ] 設定変更時の全Pod一致、スケールアウト、Worker復旧をローカルKubernetesで検証する
  - [ ] Secretへ認証情報を分離し、マニフェストへ秘密値を直接記載しない

## 実施時の共通ルール

- 各Issueでは対象となる要求ID（`F-*` / `NFR-*`）とADR番号をテスト名または変更記録へ紐付ける。
- 未指定の閾値はコードへ直書きせず、単位・初期値・バージョンを持つ設定として合意する。
- ECSの生成・削除・イベント確定はCommand Buffer経由に統一し、同一tickの二重計上を防ぐ。
- Phase 1から固定乱数seed、イベント連番、状態ハッシュを使い、Phase 3の分散検証へ同じ決定性を引き継ぐ。

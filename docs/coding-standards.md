# コーディング規約・設計ガイド

## 1. 単体テストの設計方針

『単体テストの考え方/使い方』の原則に従い、テストは実装詳細ではなく、利用者やドメインエキスパートが理解できる観察可能な振る舞いを検証する。

### 1.1 ドメイン言語による命名

- `[Method]_[Scenario]_[Expected]` のような固定テンプレートによる機械的なテスト名は禁止する。
- テスト名は、ドメインエキスパートが理解できる自然言語のストーリー文またはわかりやすい和文で記述する。
- テスト名には、検証対象の観察可能な振る舞いを表現する。

### 1.2 単体テストの4柱

次の4要素のバランスを最適化する。

- 退化への保護
- リファクタリング耐性（偽陽性の排除）
- 迅速なフィードバック
- 保守性

### 1.3 観察可能な結果の検証

- システム内部のプライベートな状態やアルゴリズムではなく、観察可能な最終結果（Observable Outcome）を Assert する。
- 実装詳細に結びつく検証や、過剰な Mock/Stub を避ける。
- 依存関係の差し替えは、テストの独立性や外部境界の制御に本当に必要な場合に限定する。

### 1.4 AAA パターン

テストコードでは、次のコメントでフェーズを明示的に分離する。

```typescript
// Arrange
// Act
// Assert
```

## 2. Clean Code 開発原則

### 2.1 意図が明確な命名

- 変数・関数・クラス名は、それがなぜ存在するのか、何をするのか、どう使われるのかが伝わるように命名する。
- 暗号的な略称や、文脈がなければ意味を説明できない短縮名を使用しない。

### 2.2 単一機能の関数

- 関数は短く保ち、1つのことだけを行う。
- 関数内の抽象化レベルを統一する（SLAP: Single Level of Abstraction Principle）。
- 副作用を持つ処理と純粋な計算処理を分離する。

### 2.3 副作用の排除

- 関数宣言や名前から予期できない隠れた状態変化を発生させない。
- グローバル状態の更新や意図しないミューテーションを避ける。
- 状態を変更する処理は、責務と境界を明確にし、必要な呼び出し側から把握できるようにする。

### 2.4 マジックナンバーの排除

- 数値や文字列の直書きを禁止する。
- 必ず意図の伝わる名前付き定数へ抽出する（例: `src/constants.ts`）。

## 3. Martin Fowler 設計・リファクタリング原則

### 3.1 コードの匂い（Code Smells）の察知と排除

- **Long Function / Large Class**: 関数やクラスが大きくなりすぎた場合は、直ちに Extract Function / Extract Class で責務を分割する。
- **Feature Envy（機能の羨望）**: 別のオブジェクトのデータを頻繁に扱う関数は、そのデータを持つ適切な場所（System / Component）へ Move Function する。
- **Primitive Obsession（基本型への執着）**: 意味を持つ数値や文字列を直接受け渡さず、Value Object や型定義へ置き換える。
- **Data Clumps（データの群れ）**: 常にセットで渡される引数群は、構造体やインターフェースへまとめる。

### 3.2 リファクタリングの基本動作

- **Green-to-Green（緑から緑へ）**: リファクタリングの前後で既存の単体テストがすべて合格することを確認し、振る舞いを変えずに内部構造だけを改善する。
- **Composed Method（構成されたメソッド）**: 関数の処理フローを、同じ抽象化レベルにある小さな関数呼び出しだけで構成する。

### 3.3 アーキテクチャ・設計パターン原則（Bliki / PPoEAA）

- **CQS (Command Query Separation)**: 関数は状態を変更するコマンド（副作用あり・戻り値なし）か、状態を問い合わせるクエリ（副作用なし・戻り値あり）のどちらか一方に限定する。両方を同時に行わない。
- **YAGNI (You Aren't Gonna Need It)**: 現在必要とされていない将来の拡張性のための抽象化やオーバーエンジニアリングを避け、現在の要件を最もシンプルに解決する。
- **ユビキタス言語（Ubiquitous Language）の反映**: 変数名・関数名・型名には、開発者だけの用語ではなく、プロジェクトのドメインモデル（生態系、捕食、個体数、栄養度など）で合意された語彙を使用する。

## 4. 進化的アーキテクチャ原則

### 4.1 適合度関数（Fitness Functions）による自動保護

- **パフォーマンス・メモリのガードレール**: 1フレーム（60fps = 16.6ms）あたりの処理時間の上限と、メインループ内のメモリ割り当て（`new` による GC 誘発）の有無を、テストやベンチマークで自動検証できる構造にする。
- **依存関係・境界の自動検証**: コアロジック（ECS ドメイン）が DOM API や Web Audio API などのプラットフォーム依存処理へ直接依存していないことを、テストコードで機械的に検証できるようにする。

### 4.2 増分変更（Incremental Change）と変更可能性の確保

- **小さな可逆的ステップ**: 機能変更やリファクタリングは小さなステップに分け、互換性を保ちながら実装と検証（テストのパス）を繰り返す。
- **モジュール性と遅延結合**: 分散スケールアウトや外部 I/O など、今後変更される境界には適切なインターフェースを挟み、システム構造を柔軟に変更可能にする。

## 5. Clean Architecture 設計原則

### 5.1 関心の分離

次の責務を完全に分離する。

- コア領域: ECS による純粋なシミュレーション計算とドメインロジック
- UI: 操作パネルと DOM 操作
- 描画: Canvas API
- 音響: Web Audio API

### 5.2 依存関係逆転の原則

- 高レベルなドメインロジックは、低レベルな詳細へ直接依存しない。
- 具体的にどの描画ライブラリやサウンド Web API を使うかは、抽象化された境界の外側で決定する。
- 詳細の変更がコア領域の変更を要求しない依存方向を保つ。

### 5.3 境界の保護

- DOM 操作や Web Audio API などのプラットフォーム依存処理は、専用のアダプターまたはシステムに閉じ込める。
- コアのデータ構造（TypedArray/ECS）へプラットフォーム依存の詳細を持ち込まない。
- モジュール間のデータ契約を明確にし、境界を越えるデータは必要最小限にする。

## 6. パフォーマンス指針

60fps の描画・計算ループ（メインフレーム）内では、メモリ割り当てによる GC を徹底して回避する。

- `new` 演算子による毎フレームのオブジェクト生成を避ける。
- 事前割り当てした TypedArray、リングバッファ、再利用可能なワーク領域を活用する。
- ループ内の一時配列、コールバック、クロージャ、文字列生成を避ける。
- 頻繁に使う数値データは連続したメモリ領域に配置し、必要に応じて SoA（Struct of Arrays）で保持する。

## 7. プロジェクト固有の適用

## 7.1 Conventional Commits

コミットメッセージは `<type>(<scope>): <short summary>` 形式とし、`type` は `feat`、`fix`、`refactor`、`test`、`docs`、`perf` のいずれかに限定する。要約は簡潔な命令形で書き、無関係な変更を一つのコミットへ混在させない。

テストを実装・変更する場合は、`docs/test-strategy.md` の技法を適用し、対象要件 ID をテスト名またはコメントへ記載する。

- 生物シミュレーションは厳格な ECS パターンで実装する。Entity は数値 ID、Component はデータ、System は処理ロジックとして扱う。
- Canvas 2D による生物描画は 1x1〜3x3 ピクセルの極小ドットを基本とする。
- 音響は Web Audio API で動的に生成し、外部音声ファイルやストリームに依存しない。
- コアロジック、UI、描画、音響の責務を混在させない。

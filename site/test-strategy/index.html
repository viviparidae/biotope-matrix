    テスト戦略

    1. 目的とトレーサビリティ

    要求仕様書と Feature ファイル、実装テストの3層を必ず対応づける。要求 ID は REQ-* とし、Feature のタグ、describe / it 名、そして CI 発行レポートで一貫して追跡可能にする。要求網羅率は、対象要件に少なくとも 1 件の合格テストが紐づいた数を総数で割って算出し、未カバー要件を PR のレポートに出力する。

    2. 三層トレーサビリティ

    1. 要件層: docs/requirements.md に要件 ID、概要、評価基準を記載する。
    2. BDD 層: tests/features/*.feature に @REQ-... を付けてシナリオを記述する。
    3. 実装層: vitest のテスト名、コメント、it のラベルに REQ-... を付与する。

    例: REQ-PRED-001 は要求仕様、Feature での @REQ-PRED-001、そして predation テストの it('REQ-PRED-001: ...') が同一の要求を参照する。

    3. ブラックボックス設計技法

    • 同等性分割: 有効・無効の入力クラスを分け、代表ケースを選ぶ。
    • 境界値分析: 閾値 N では N-1, N, N+1 を最低限検証する。
    • 状態遷移テスト: 遷移を N=1 で確認する。
    • ペアワイズ法: 組み合わせる場合は、全組み合わせではなく全ペアの検証のみに絞る。

    4. テスト構造と品質ゲート

    • 単体テストは AAA を守り、Arrange / Act / Assert を明示する。
    • 固定乱数を注入し、判定ロジックを決定的にする。
    • ECS コアは DOM / Canvas / Web Audio へ依存しない。
    • PR の品質ゲートは、型チェック、vitest、Feature 検証、要求 ID 未カバー確認で構成する。

    5. Cucumber と受入テスト

    利用者やドメインエキスパート向けの振る舞いは tests/features/*.feature に Gherkin で記述し、tests/steps/*.steps.ts に step 定義を分離する。各 feature の先頭タグとして要求 ID を付け、pnpm test:cucumber で受入テストを実行する。step 定義は Arrange / Act / Assert を混在させず、観察可能な結果を検証する。

    6. 追跡表

    要件 ID 対象 主な技法
    REQ-PRED-001 条件付き捕食 境界値、ペアワイズ
    REQ-CANN-001 飢餓時同種捕食 状態遷移、境界値
    REQ-MORPH-001 形態とサイズの遺伝 同等性分割、境界値
    REQ-FLOCK-001 群れ行動 同等性分割、性能測定
    REQ-ARCH-001 適合度関数と CI パフォーマンスゲート、依存境界
    REQ-ARCH-002 メモリ再利用とシリアライズ 境界値、回帰回数

    7. CI での実行方針

    • pnpm test で単体・統合・受入の回帰を実行する。
    • .github/workflows/fitness.yml で 1 フレーム処理時間 と 起動依存チェック を自動実行する。
    • 観測不能な要件は、Feature への紐付けと要求 ID の明示を必須とする。

    8. シンセティックトランザクションによる長期生態系監視

    生態系の長期持続性は、対象の推移を事前に定義した合成シナリオで観測し、数千ステップにまたがる振る舞いを「絶滅率」「回復率」「多様性指数」というヘルス指標で監視する。

    • 絶滅率: extinctionRate = zeroPeriods / totalSamples
    • 回復率: recoveryRate = (populationAfterRecovery - populationAfterDisaster) / max(populationAfterDisaster, 1)
    • 多様性指数: diversity = (grass + herbivores + carnivores) / max(1, totalPopulation)
    • 安全閾値: herbivores > 0 かつ carnivores > 0 かつ populationAmplitude <= 6..8 を満たす状態を「安定」と判定する

    実装では src/tests/syntheticTransaction.test.ts に Arrange / Act / Assert の合成テストを置き、ノーレンダリングで 10,000 ステップと 3,000 ステップの長期監視を実行する。各テストは観察可能な結果だけを確認し、複雑な実装詳細や描画依存を検査しない。
